## Answer

У вступі RO/EN додано реалістичний телефон із вісьмома станами запису:
пошук → форма → послуга → спеціаліст → дата → час → підтвердження → успіх
і майбутній запис. Дані вигадані й узгоджені; підпис явно вказує на користувача,
який уже увійшов, і відсутність справжнього бронювання.

`PhoneDemo.astro` та `phone-playback.ts` надають спільний корпус і незалежне
керування відтворенням. `ClientBookingDemo.astro` та `booking-demo.ts` містять
статичні екрани й локалізований сценарій. Є один автоматичний цикл, пауза,
продовження, повтор, зупинка поза екраном або у прихованій вкладці, збереження
ручної паузи й статичний режим reduced motion/no-JS. Бізнес-ілюстрація працює
як раніше.

Локальні клієнтський застосунок і BookMe Salon перевірено на однакових
демонстраційних даних без реальних API. [Звіт і знімки для порівняння](../../../design/booking-demo/README.md)
містять вихідну ревізію застосунку, відмінності подання, RO/EN на
320/768/1440px і доступні описи.

Перевірки: `npm run check`, `npm run build` і `npm run package:site` пройшли.
Повний `npm test`: **962 passed, 112 expected skips**, без помилок і повторних
спроб. Axe перевіряє всі вісім кадрів обома мовами; окремі тести перевіряють
клавіатуру, видимість вкладки, зміну reduced motion та відсутність API/дозволів.
Обидві головні сторінки: **1 409 B JS / 6 854 B CSS gzip**.
`npm run test:lighthouse`: усі **48 аудитів** пройшли; performance 98–100,
accessibility / best practices / SEO — 100 у кожному запуску. Найбільші
медіани: LCP 1 654 мс, CLS 0,0794, TBT 0 мс.

Ручний огляд знімків і дерева доступності виконано. Нативні VoiceOver,
клавіатурна сесія, 400% zoom, перемикання OS reduced motion і взаємодія з
фоновою вкладкою залишені явно pending у звіті; автоматизовані перевірки
не подані як результати цих ручних перевірок.
